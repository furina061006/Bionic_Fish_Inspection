## 二、`heave` 不再下发

单关节尾鳍 + 浮在水面 ⇒ 没有深度轴可指令。`ChannelMap.heave` 默认从 `3` 改为 `None`。

- 实测：下发字典从 `{3,4,5}` 变成 `{4,5}`
- 90 个测试全绿：`heave` 本来就不参与 `plant` 的动力学，合成闭环行为不变
- 只改**轴集合**，通道号仍沿用参考平台的 ArduSub 布局且仍是 `UNVERIFIED`——现在确定的是「有哪些轴」，不是「哪个通道」

## 三、判别器：绝对暗度（机制成立，但在渲染器里被否定）

推理链：

1. `MarkerDetector` 用**黑帽（相对暗结构）**做检测，阈值 40
2. 在白管上，纯黑圆与中灰圆的响应分别是 ~230 与 ~155 —— **都远超 40**
3. 所以 `discriminator="none"`（默认）会把 5 个干扰点全收下 ⇒ **−15 分**
4. 而相对量**原理上**分不开"黑"与"比白暗"；只有**绝对灰度**能分
5. `MarkerCand.val` 已经在字段里 —— 不需要多算任何东西

于是新增 `discriminator = "darkness"`。同时**实测**了合成场地上的数值，见下一节。

### 中途改正的一处（记下来，这是花了时间的）

我第一版把 `val_band` 默认值写成 `(0.0, 60.0)`，理由是「漏油点是纯黑，60 够宽松」。测完发现两个问题：

1. 合成场地里漏油点的 `val` 实测是 **46…60**（不是 `leak_bgr=(18,18,20)` 暗示的 ~20——水体的加性雾化把它抬高了），**上界 60 只擦着过去 0.1 个灰度级**
2. 更要紧的是**不一致**：`hue_band_deg=(0,180)`、`fill_ratio_band=(0,1)`、`offset_band_frac=(0,1)` **全都是「全收」**。判别器的语义是「给一个待标定的槽位」，不是「替你决定阈值」

所以改成 `(0.0, 255.0)`，并把实测区间写进注释。**默认配置下选择一个判别器不会悄悄拒掉候选**——否则默认配置会「什么都不报」，而那种失败看起来像感知坏了。加了测试守着这条。

### 实测数据，以及**第二次改正**（这次改正推翻了本轮的结论）

第一版测量是**单帧、标记居中、两个观察方向**：

| 类别 | `val` | `contrast` |
| --- | --- | --- |
| 漏油点 | 46…60 | 156…171 |
| 误识别点 | 122…137 | 2…19 |

我据此写了「上界取 90 左右即可分开」，并把它写进了 `config.py` 的注释、`vision.md` 和这条日志。

**然后走了一次 CLI 端到端验证**（`--config` 带 `darkness` + `val_band [0,90]`），上报数从 8 掉到 **5**。**判别器拒掉了 3 个真漏油点。**

于是把上界从 60 扫到 255（每档跑一整场合成闭环）：

| 上界 | 上报数（真值 8） | 被暗度拒掉的候选 |
| --- | --- | --- |
| 60 | 5 | 203 |
| 90 | 5 | 185 |
| 100 | 5 | 181 |
| 110 | 7 | 153 |
| **120** | **8** | 71 |
| 130 | 8 | 42 |
| 150 | 8 | 1 |
| 255 | 8 | 0 |

**结论反了**：要保住 8 个真漏油点，上界必须到 **120**；而误识别点的区间从 **122** 起。**两个区间重叠，在这个渲染器里绝对灰度分不开它们。**

单帧的 46…60 是**取样不足造成的假象**——渲染器有横跨整帧的光照梯度，同一种标记出现在画面不同位置时，漏油点自己的 `val` 会爬到 120 附近。

两处已经改正：`config.py` 的 `val_band` 注释、`vision.md` 的判别器小节（都换成了上面这张扫描表）。测试也改了——原来硬写「`val < 90`」，现在**从两次测量算出中点**当上界，避免把一次未标定的数字伪装成阈值。

**教训**：一次单帧探针**不足以**支撑「这个特征能分开两类」的结论。探针只能证明机制存在，**能不能分开必须跑完整场再看**——尤其是渲染器/真实环境里有跨画面的光照梯度时。这一次是端到端那一步把它抓出来的。

（`contrast` 那一列看着分得很开，但那是**渲染器自己猜的干扰点外观**造成的，不构成关于真实干扰点的证据，不能用。）

## 四、备注：统一的中文定位块

审阅者说「代码难读懂」。"读不懂"的根因不是单行难看，而是**从模块内部推不出它何时被调用**。所以每个模块的 docstring 末尾加一个固定形状的中文块：

```
在链路里的位置
    每帧第 N 步（共 13 步，见 runtime.Runner._iterate），由 runtime 调用
    上游：<类型名>
    下游：<类型名>
    跨帧状态：有/无（有就点名关键字段）
    概念：.dsh/agents/runtime-flow.md 第 X 节
```

- **为什么混两种语言**：标识符与 docstring 主体保持英文（与代码一致），导航信息用中文（读者是本项目的人，全部知识库都是中文）。**导航读得快比语言一致更重要**
- 约定已写进 [writing](../agents/writing.md)，含四条要求
- `runtime.py` 与 `__init__.py` 是例外：前者本身就是顺序，后者改成了全包阅读指南（含「先跑起来再读循环」与命名提醒）

## 五、顺手抓到的一个**先前就存在**的文档 bug

跑「只跑感知层」那条命令时它报错：

```
python -m unittest tests/test_perception.py
ModuleNotFoundError: No module named 'tests.test_perception'
```

**不是本轮引进的**——把本轮改动 `git stash` 掉再跑，同样报错。原因：`python -m unittest <路径>` 会把路径当成**模块名**去 import，于是要求 `tests` 是一个包；而 `tests/` 恰恰没有 `__init__.py`。README 自己还写着「不要把 `tests/` 当包调用（它不是包）」——**那条命令正好违反了它下面那句话**。

已改成实测可用的形式：`python -m unittest discover -s tests -p "test_perception.py"`（30 个测试 0.5s 跑完）。

**教训**：文档里的命令没有测试守着，只能靠**真的去跑一遍**才会发现。这次是「端到端验证」这个习惯第二次抓到问题（第一次是第三节的判别器）。
