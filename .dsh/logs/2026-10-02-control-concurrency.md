# 2026-10-02 — 并发模型：按时间尺度切线程，输出只有一个写者

## 目标

用户在读完参考项目 `_pipe1` 与 `_turn_first` 之后提出一个设想：

> 整成两个线程——A 实时控制空间六轴，B 只有在拐弯逻辑激活时控制水平四轴，然后 A 看情况决定是否抢控制权。

要回答的是「这么切行不行」，并把结论固化下来（本文件是过程记录；现行设计进了 [`../agents/architecture.md`](../agents/architecture.md) 第七节与 [`../agents/control.md`](../agents/control.md)）。

## 结论先说

**这个直觉抓对了问题（分层），但用错了工具（抢）。**

- 值得保留的：把「一直要稳的东西」和「只在事件发生时干活的东西」分开——这正是串级控制的内环/外环分层
- 必须去掉的：两个执行流各自写输出、靠优先级去抢

## 一、先破掉一个前提：A 和 B 都是外环

用户的分工听起来像「A 是内环、B 是外环」。但要先看清一件事：**我们发的是 `RC_CHANNELS_OVERRIDE`，也就是遥控杆位。**

杆位 → 姿态 → 推力这一整套，是飞控每几毫秒跑一遍的。所以**内环已经在飞控里了**，A 和 B 谁都不是内环，它们是两个并列的外环。

再看冲突点：A 的巡线控制用 **ch4（偏航）** 修正横向偏差，B 的转弯也**用 ch4**。所以冲突不是「6 轴 vs 4 轴」，而是**两个策略抢同一根摇杆**。分成两个线程完全不解决这个冲突，只是把它从「有逻辑的争用」变成「看谁先抢到」。

## 二、输出会撕裂成什么样

`aim()` 内部不是一次原子操作，是 6 次独立发送（`move/move.py:47-54`）：

```python
set_rc_channel_pwm(3, pwm1)   # 消息 1
set_rc_channel_pwm(4, pwm2)   # 消息 2
set_rc_channel_pwm(5, pwm3)   # 消息 3
set_rc_channel_pwm(6, 1500)   # ...
```

假设 A 想发 `aim(1420, 1500, 1590)`（定高、回中、全速巡线），B 想发 `aim(1420, 1650, 1490)`（定高、右转、减速）。两个线程交错，完全可能得到：

```
ch3 = 1420   ← A（深度没问题）
ch4 = 1650   ← B（在急转弯！）
ch5 = 1590   ← A（全速前进！）
```

**「一边急转弯一边全速冲」——A 和 B 都不想要这个状态，而它恰好是物理上最容易撞壁的组合。**

更糟的是三点：交错**不确定**（实验室复现不出、现场出）、出错时**没有任何日志**能指出是谁发的、`sleep` 位置/GIL 切换/串口缓冲都会影响结果。

## 三、顺手查实的一件事：RC override 会超时

ArduPilot 官方文档（[RC Input](https://ardupilot.org/dev/docs/mavlink-rcinput.html)）写明：

> If the MAVLink RC input stops, ArduPilot falls back to regular RC input **within a few seconds**. This timeout is configurable using the `RC_OVERRIDE_TIME` parameter.

**这条把「多久发一次指令」从性能问题提升成了正确性问题。** 回头看参考项目就更明显：`_turn_first` 是 `aim → sleep(1) → aim → time.sleep(2)`，**3 秒里一条消息都不发**，恰好卡在超时边缘。

顺带得出一个设计结论：并发改造里**最该独立出来的不是「轴」，是「发指令」**——它必须准点，不能挂在感知的节奏上。

【待验证】本平台 `RC_OVERRIDE_TIME` 的实际取值，要去飞控参数表上读。

## 四、正确的切法：按时间尺度，不按轴

并行化的依据是两个问题：**哪些东西必须按自己的节奏跑**、**哪些东西会阻塞**。

| 角色 | 节奏 | 会不会阻塞 | 产出 |
| --- | --- | --- | --- |
| 感知（相机 + CV + 降频检测） | 5–15 Hz，抖动大 | **会**（推理数百毫秒） | 带时间戳、不可变的观测 |
| 控制 | **固定 ≥20 Hz** | 不会 | **唯一的执行器写点** |
| 日志 / 上报 | 事件驱动 | 不应阻塞控制 | 永不触碰执行器 |

三条规矩：

1. **只有一个线程写输出。** 无论几个策略，最终都汇总到一个 `aim()` 调用点
2. **转弯不是线程，是状态。** `mode == 'CORNER'` 时由转弯策略填那张表，其它时候由巡线策略填；同一时刻只有一个人填。交接点已经存在：`Decision.yaw_override_us`
3. **观测带时间戳 + 看门狗。** 超过阈值未更新就回中立/停

第 3 条不是洁癖：**参考项目现在的失败模式是「卡死」（明显、好发现）；改成并发之后变成「拿着几秒前的画面自信地开」（隐蔽、更危险）**，因为程序看起来还在正常工作。

这也回答了「A 看情况决定是否抢控制权」——**不存在抢**。抢意味着结果取决于调度时机；正确形式是「显式的模式所有权 + 一处判定条件」。
