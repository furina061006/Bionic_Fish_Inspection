## 为什么这一层值得单独一份文档

上报是**唯一能同时加分和扣分**的动作，而且两条方向不对称：

| 动作 | 分数 |
| --- | --- |
| 正确上报一个真实漏油点 | `+5`（8 个上限 40） |
| 误报一个（实际无漏油处上报） | `−3`（累计最多 `−24`，即 8 次） |
| 漏报一个真实漏油点 | `0`（只是拿不到那 5 分） |

- 【推导】设候选点为真实漏油点的概率为 `p`，则上报的期望收益为 `5p − 3(1 − p) = 8p − 3`，**只有 `p > 3/8 = 0.375` 才值得上报**
- 【推导】**已确认 8 个之后，继续上报的期望上限为 0、下行仍为 `−3`**，因此第 8 次成功上报后应显著提高门槛
- 【设计】结论：这一层不是「提高召回」，而是**在召回与误报之间做显式的概率判决**。任何「看到黑点就报」的实现都违反 [不变量 2](invariants.md)

## 三道闸（必须全部通过才上报）

```
MarkerCand[]
  │
  ├─ 闸 1 几何门控      候选必须在灯带中心线邻域内；形状 / 面积 / 圆度符合标定窗口
  │                     ↓ 淘汰：池底杂物、阴影、水面焦散暗纹、灯带缺口
  ├─ 闸 2 时序确认      同一候选在连续 N 帧被稳定跟踪；像素面积随接近单调增长；
  │                     横向位置平滑；置信度累积超阈值
  │                     ↓ 淘汰：单帧噪声、误识别点（若其外观特征不稳）
  ├─ 闸 3 身份去重      该候选对应的轨迹是否已上报过；冷却期内不重复触发
  │                     ↓ 淘汰：同一漏油点的重复上报
  └─ → ReportEvent
```

- 【设计】三道闸的**判定过程必须逐条可打日志**（每个候选在每一闸的输入与结论）。否则现场无法区分「没检测到」和「被闸掉了」——这是 [troubleshooting](troubleshooting.md) 的第一分叉
- 【设计】闸 1 里**独立使用一条「起终点优先」规则**：在起终点区附近，暗带优先解释为分界线，不作为漏油点候选（[不变量 6](invariants.md)）
- 【待验证】`N`（确认帧数）不能凭感觉定：它受**速度 × 帧率 × 视场**共同约束——标记在视野中停留的帧数是 `N` 的物理上限。必须先算清再取值

## 触发时刻：「重合」而不是「看见」

- 【事实】原文规定「当机器鱼与漏油点**重合**时，需通过声光信号或数据回传实时上报」（[competition](competition.md)）
- 【设计】因此触发条件不是「第一次检测到」，而是**预测的沿路径重合时刻**：
  - 闸 2 完成确认时，标记还在鱼前方，用 `s`（沿路径里程）预测它何时到达鱼体检测模块下方
  - 到达重合时刻触发 `ReportEvent`
  - 若确认直到重合都没完成，则**放弃该点而不是补报**（补报时视觉已移出视野，无法确认，等于赌博式误报）
- 【设计】需要补偿端到端延迟（曝光 → 判决 → 执行器 / 声光）：触发点提前一个延迟量。该延迟必须实测（[operations](operations.md)），不许猜
- 【设计】⚠️ 与闸 2 的张力：确认需要时间，而重合时刻要早于「移出视野」。这直接给出**速度上限**——跑太快会让确认来不及完成。这个约束要和 [control](control.md) 的速度档位一起定，不能分开定

## 去重：按轨迹身份，不是按时间

- 【设计】不用「冷却 N 秒」，因为：
  - 慢速时纯时间冷却会在两个真实漏油点之间误抑制
  - 快速时又会把同一个点的多帧检出错判成两次上报
- 【设计】正确做法是**候选轨迹跟踪 + 身份去重**：
  1. 用帧间连续性把 `MarkerCand` 关联成轨迹（由远及近、面积单调、横向平滑）
  2. 一条轨迹最多产生一次 `ReportEvent`
  3. 叠加一个**很短的**冷却期（用于抑制同一条轨迹在关联抖动下分裂成两条）
- 【事实】8 个漏油点 + 5 个误识别点共 13 个标记分布在约 6m 路径上，平均间距约 460mm，**小于鱼体长度 600mm**
- 【设计】**结论**：所以**不能**用纯距离窗口去重（会把相邻两个真实漏油点合并成一个）。轨迹身份是唯一可靠手段，里程 `s` 只用于预测重合时刻与日志

## 上报信号设计

上报有两条并行通路，**必须由同一个 `ReportEvent` 驱动**：

| 通路 | 作用 | 要求 |
| --- | --- | --- |
| 声光信号 | 满足「实时上报」；线上赛靠摄像机判分 | 【事实】线上赛「若视频中无法辨别信号，该得分点视为无效」 |
| 无线数据回传 | 数据留档 | 【事实】允许的通路之一 |
| 语音播报 | 独立得 10 分，漏播一个 `−2` | 【事实】语音内容需清晰可辨 |

- 【设计】声光信号按**被摄像机拍到**来设计，不按「我们自己看得见」：
  - 光：高亮度、指向池壁 / 水面方向、颜色与池底湖蓝及灯带白光**明显区分**（避免被判为灯带反光）
  - 持续时长：足够跨越摄像机帧率并被人眼与裁判识别（量级 ≥ 0.5s），且必须在「重合」时刻立即起亮
  - 声：音调与语音播报错开，避免互相掩盖
- 【设计】语音内容：简短、可辨、含序号（例如「第 N 点」），**一次上报只播报一次**，绝不重复
- 【设计】上报与播报**共用 `ReportEvent`**，禁止各写一套触发条件（[不变量 5](invariants.md)）——两套条件一定会漂移，造成「报了不播」直接扣分
- 【待验证】语音方案（TTS / 预录音频 / 蜂鸣编码）与音量在 260mm 水深与现场噪声下的可辨性，必须在调试窗口实测并由录像确认

## 误报来源清单（按危险程度）

| 来源 | 危险度 | 拦它的闸 |
| --- | --- | --- |
| **起终点黑色胶带** | 最高：本身就是黑色，且必然出现 | 闸 1 的「起终点优先」规则 + 状态机上下文 |
| **误识别点**（5 个，外观未知） | 高：故意设置的干扰项 | 闸 2（若外观可判别则升级为闸 1）；判别特征见 [vision](vision.md) |
| 鱼体自身 / 气泡阴影 | 中 | 闸 1 的几何门控（阴影形状不规则、位置随姿态变化） |
| 水面焦散暗纹 | 中 | 闸 2 的时序一致性（焦散纹闪动、不随接近单调增长） |
| 池底杂物 / 污点 | 低 | 闸 1 的尺寸窗口 |
| 灯带本身缺口 | 低 | 闸 1 的圆度 + 与中心线的相对几何（缺口是沿灯带方向的狭长形） |
| 已上报点重复触发 | 中 | 闸 3 身份去重 |

## 评分与决策的联动

- 【设计】维护一个显式的**上报计数器**：`attempts`（触发次数）与 `confirmed`（本队自认正确的次数）。注意 `confirmed` 是自认的，不是真值
- 【设计】当 `attempts ≥ 8` 时把决策阈值从 `0.375` 显著上调（因为 40 分上限已用尽，剩余上行收益为 0）
- 【设计】若某候选 `p` 处于 `0.375` 附近的灰区，**优先放弃**：5 分的边际收益不值得 3 分的确定性风险，而且要留出「创新 / 完成度」这些不扣分的分项
- 【待验证】`p` 的实际估计方式（贝叶斯累积 / 特征打分 / 简单计数）需在离线数据集上标定，并用留出样本验证**误报率**，而不是只看检测率
