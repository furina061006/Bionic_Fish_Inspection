## 一、工具链（已定）

- 【事实】用户指定：**本项目工具链与 [`reference/pipe_inspector_raspberry-main/`](../../reference/pipe_inspector_raspberry-main/) 一致**。逐项出处见 [reference-pipeline](reference-pipeline.md) 第 1 节
- 【事实】赛题 PDF 对运行环境**没有任何规定**——操作系统、语言、中间件、算力位置全部自由。所以这是**用户的选择**，不是赛题的要求

| 层 | 选择 |
| --- | --- |
| 主控 | 树莓派（Raspberry Pi），Python |
| 相机 | USB 摄像头，OpenCV `VideoCapture` |
| 飞控通信 | MAVLink over 串口，`pymavlink` |
| 控制指令 | **`RC_CHANNELS_OVERRIDE`**：发的是遥控杆位，飞控负责稳定与定深 |
| 通道布局 | ArduSub 默认：3=垂推 / 4=偏航 / 5=前进 |
| 检测 | 经典 CV 为主；ONNX Runtime 跑 YOLOv5-Lite 是**保留但未启用**的通路 |
| 外设 | `RPi.GPIO`：声、光 |
| 航向源 | MAVLink `ATTITUDE`。**是否存在未确认**（backlog `#12`） |

**输出节拍是正确性要求，不是性能优化**：

- 【事实】`RC_CHANNELS_OVERRIDE` **会过期**：ArduPilot 官方文档写明「若 MAVLink RC 输入停止，飞控在几秒内回落到常规 RC 输入」，超时由 `RC_OVERRIDE_TIME` 参数配置（[ArduPilot: RC Input](https://ardupilot.org/dev/docs/mavlink-rcinput.html)）
- 【推论】所以「多久发一次指令」与「发什么」同等重要。**一个只在决策变化时才发指令的实现，会在任何超过该超时的停顿里静默失去控制**
- 【待验证】本平台 `RC_OVERRIDE_TIME` 的实际取值（在飞控参数表上读）——它直接决定控制环允许的最大发送间隔
- 参考项目踩到的具体形式见 [reference-pipeline](reference-pipeline.md) 第 6 节；由此推出的并发规则见[第七节](#七并发模型谁在什么时候能写输出)

**车体的轴集合（决定「哪些通道存在」）**：

- 【事实】队内确认（2026-10-02）：**单关节尾鳍** + **一直浮在水面**。所以只有**两个轴**——前进与偏航——**没有深度轴**，也不会有定深环
- 【事实】接口由我们自己设计，没有现成契约；`ChannelMap.heave` 默认已置 `None`。见 [hardware](hardware.md)
- 【待验证】推进机构自研是否满足原文「基于组委会认证的统一仿生平台改装」的口径——这是**资格问题**，不是技术问题，见 [hardware](hardware.md) 的合规待确认项

**从参考项目继承时要改掉的两条接口习惯**：

1. **只开一条 MAVLink 连接。** 参考项目在 `move.py`、`arm_disarm.arm()`、`disarm()` 里各开一条，三个对象抢同一串口的心跳与消息。**MAVLink 流只有一个读者**——控制输出与遥测必须共用同一条连接。
2. **解锁要校验回执。** 参考项目把 `motors_armed_wait()` 注释掉并**无条件打印 `Armed!`**，解锁失败会静默继续。

## 二、模块边界，以及为什么切在这里

```
     ┌──────────────────────────────────────────────────────────┐
     │  感知  perception      「这一帧看到了什么」              │
     │    灯带中心线 / 暗斑候选 / 起终点黑带                    │
     └───────────────┬──────────────────────────────────────────┘
                     │  LineObs / MarkerCand[] / CrossObs
     ┌───────────────▼──────────────────────────────────────────┐
     │  决策  reporting       「该不该上报」                     │
     │    轨迹关联 + 三道闸 + 概率判决 → ReportEvent            │
     └───────────────┬──────────────────────────────────────────┘
                     │
     ┌───────────────▼──────────────────────────────────────────┐
     │  状态  fsm             「现在跑到哪了、该快还是该慢」      │
     │    状态机 + SafetyMonitor（四条硬终止）                   │
     └───────────────┬──────────────────────────────────────────┘
                     │  Decision { state, 目标速度, 弯角标志, 转向覆盖 }
     ┌───────────────▼──────────────────────────────────────────┐
     │  控制  control         「给定目标怎么打舵」                │
     │    串级纯追踪 → 各通道 PWM                                │
     └───────────────┬──────────────────────────────────────────┘
                     │
     ┌───────────────▼──────────────────────────────────────────┐
     │  平台  platform        「怎么发出去、怎么对外发信号」      │
     │    MAVLink RC override + 声光/语音（订阅 ReportEvent）     │
     └──────────────────────────────────────────────────────────┘

     横切：config（全部可调参数 + 标定，唯一住所）
           arena / plant（合成场地 + 占位动力学）—— 只在没有硬件的阶段存在
```

**为什么这样切——判据是「排查时分得清哪一层错了」**：

- `perception` 只回答「看到了什么」，**不含任何策略**。它若顺手决定「该不该上报」，那么一次漏报就分不清是**没看见**还是**看见了被否决**——而这正是排查的第一分叉（[troubleshooting](troubleshooting.md)）。
- `reporting` 只做概率判决。它读不到状态机，也不知道车在路线哪一段——这迫使「起终点优先」这类规则必须显式传入上下文，而不是藏在感知里。
- `fsm` 不做像素运算、不做舵量计算，只决定「状态 + 目标速度 + 是否提交转向」。
- `control` 只做「给定目标怎么打舵」，不判断该不该转。
- `platform` 是唯一的硬件出口。**它的存在让整条链路可以在没有硬件的机器上跑完**（回退到记录型实现），这是本仓库现在唯一能验证整链路的原因。

**参考项目恰好把这三件事揉在一起**：一个 `while 1` 循环里同时读队列、跑 PID、判拐角、发 PWM、开线程亮灯抓取，状态用 23 元组在函数间传递。它的 17 条缺陷清单见 [reference-pipeline](reference-pipeline.md) 第 6 节——**清单里超过一半是「边界没切」的直接后果**。

## 三、模块间必须成立的耦合（**最容易漏、漏了最难查**）

这一节是本文最重要的部分。下面每一条都是两个模块之间**必须一起考虑**的关系；任何一条被当成「两个独立模块」处理，都会产生一整类只能靠运气发现的故障。

| # | 耦合 | 后果 / 证据 |
| --- | --- | --- |
| 1 | **转向权限 ∝ 前进速度**（欠驱动尾鳍车没有侧推） | 速度档位 ↔ 弯角 ↔ 丢线恢复三者绑死。弯角把速度降到接近零 → **转不动**，转弯必然超时；丢线恢复不保留前进分量 → **无法回正航向**。实测：弯角速度从中位附近调到 `1525` 后，弯角阶段从 100 帧降到 62 帧 |
| 2 | **「重合」不能用里程判定**（没有里程计） | 上报触发 ↔ 感知：用**固定图像行**判「已到目标下方」，行阈值来自标定。时间更不行——速度一变就错 |
| 3 | **弯角不能靠巡线控制律飞** | `fsm` ↔ 航向源 ↔ `control`：灯带一离开视野就没有航向参考。必须「**提交一个转向指令 + 用独立判据终止**」。终止判据优先级：转过 90°（需航向源）> 限时 > 双向搜索 |
| 4 | **上报的判决阈值由评分决定** | `reporting` ↔ [`competition.md`](competition.md)：`+5 / −3` ⇒ `p > 3/8`。**评分改了阈值就得改**；已报满 8 个后上行收益为 0、风险仍为 −3，门槛还要提高 |
| 5 | **起终点黑带与漏油点都是黑的** | 感知 ↔ `fsm`：黑带与标记在单帧上不可靠可分，必须**叠加状态机上下文**（在起终点区附近优先解释为分界线）。这不是纯视觉问题 |
| 6 | **灯带被标记遮挡** | 感知内部：标记就贴在灯带上，会在灯带掩膜上打出一个洞。**被截断的游程其中心会偏向存活的一侧**，直接把中心线拉偏。所以分割的闭运算核必须**大于标记直径**——这是正确性要求，不是平滑 |
| 7 | **像素阈值 ← 标定 ← 相机安装** | `hardware` ↔ `perception` ↔ `config`：相机型号/高度/视场未定，则「3cm 圆对应多少像素」未定，则全部面积/尺寸阈值未定。**代码里不许有未标定的尺寸常数**（[不变量 7](invariants.md)） |
| 8 | **上报与播报必须共用一个事件** | `reporting` ↔ 播报：评分把语音单列 10 分（漏播一个 `−2`），两套触发条件一定会漂移，导致「报了不播」 |
| 9 | **硬终止必须独立于状态机** | `fsm` 内部但**边界独立**：`SafetyMonitor` 与状态转移分开，因为状态机出错时保护仍然要生效。若保护写在状态转移里，一个转移 bug 会连带关掉保护 |
| 10 | **只有一帧的检测不能上报** | `reporting` ↔ 速度档位：确认需要 N 帧，而标记在视野里停留的帧数由**速度 × 帧率 × 视场**决定。跑太快 → 确认来不及完成 → 只能放弃该点。**速度上限是感知决定的，不只是控制决定的** |
| 11 | **输出只有一个写者，且它的节拍独立于感知** | `control` ↔ `platform` ↔ `perception`：RC override 会超时（第一节），所以「发指令」必须有自己的时钟；而若两个策略各写一部分通道，`aim()` 内部那 6 次独立发送会交错出「一边急转、一边全速」这种两个策略都不想要的状态。**控制权是显式的模式所有权，不是线程优先级** → [第七节](#七并发模型谁在什么时候能写输出) |
| 12 | **单关节尾鳍：推力与转向出自同一个执行器** | `control` ↔ `hardware` ↔ `plant`：尾摆**振幅**给推力、**偏置**给转向，所以**大舵量直接吃掉推力**。注意这与耦合 1 不是一回事——耦合 1 是「权限随速度变化」（两个独立轴），这里是**同一个量被两个用途争**。因此转向需求与推进需求必须**一起**决策（预算分配），不能各算各的再加起来。`plant.py` 现把两者当独立轴，**在这个意义上已知是错的**，换真机前必须重建模 → [hardware](hardware.md) |

## 四、数据流

```
相机帧
  ↓ perception：灯带分割 → 逐行游程 → 鲁棒直线拟合
  │    LineObs { valid, e_y_px, e_y_norm, e_theta_rad, curvature, confidence,
  │               strip_width_px, lookahead_px, fit, branch_px }
  ↓ perception：黑帽 → 连通域 → 形状/面积门控 + 与中心线的横向门控
  │    MarkerCand { u, v, area_px, circularity, equiv_diameter_px,
  │                 hue_deg, sat, val, fill_ratio, lateral_offset_px,
  │                 lateral_reliable, contrast }
  ↓ perception：灰度暗带 + 行跨度 + 必须横跨灯带 + 必须在画面内部 + 必须灯带可见
  │    CrossObs { detected, row, width_px, row_lo, row_hi }
  ↓ reporting：轨迹关联 → 闸1(几何) → 闸2(时序确认/接近/增长) → 闸3(轨迹身份去重)
  │             → p > 阈值 判决 → ReportEvent { track_id, sequence, row, confidence }
  ├→ platform：声光 + 语音，**订阅同一个 ReportEvent**
  ↓ fsm：状态转移 + SafetyMonitor（四条硬终止）+ 弯角推进
  │    Decision { state, target_forward_us, corner, terminal, abort,
  │               elapsed_s, off_track_s, wall_hits, yaw_override_us }
  ↓ control：外环 atan2(e_y, L) → 内环 (e_theta + e_theta_d) → PWM
  │    Actuator { channels: {通道号: PWM}, yaw_us, heave_us, forward_us }
  ↓ platform：RC_CHANNELS_OVERRIDE（未用通道填 65535 = 不覆盖）
```

**几处刻意的不对称，都是踩过坑才有的**：

- `e_theta` 是**灯带方向 − 车体航向**（灯带相对车体），所以内环误差是 **`e_theta + e_theta_d`**，不是看起来更自然的差。写成差会让航向环变成**正反馈**——而「直道 + 横向偏置」的测试**看不出来**（那里 `e_theta ≡ 0`）。
- `valid=false` 与「偏差 = 0」是两件事。**严禁用 0 冒充「没看到」**（[不变量 3](invariants.md)）。
- `lateral_reliable` 单独一个字段：灯带没定位时横向偏差无意义，评分时必须按「未知」而不是「完美居中」处理。
- `CrossObs` 只在**灯带可见**时才可能为真——「横穿灯带」这个事件没有灯带就没有定义。
- `ReportEvent` 是**唯一**对外信号的触发源；`sequence` 就是播报用的序号，保证不漏播。

## 五、状态机

```
IDLE ──start──▶ ALIGN ──对齐或超时──▶ FOLLOW
                                       │ ▲
                        丢线 ──────────┤ │── 重捕
                                       ▼ │
                                  LINE_LOST ──超 10s──▶ ABORT
                                       ▲
                FOLLOW ──弯角判据确认──▶ CORNER ──┬─ 转够角度 / 限时
                                                  └─▶ LINE_LOST（**保留提交转向**）
                FOLLOW ──黑带 + 已跑够时间──▶ FINISH_APPR ──续行──▶ DONE
```

- 【设计】`ALIGN` 单独成状态：起点区只有约 500mm，初始航向误差大，用巡线律去纠会直接压到分界线。**但 `ALIGN` 也带小前进量**——转向没速度就没有权限，而「30 秒未启动」是硬终止
- 【设计】`CORNER` 的实际判据是 **`confidence` 下降为主、`curvature` 突增为确认**。实测：逼近直角时 `confidence` 单调 0.93→0.49，而 `curvature` 只在最后 50mm 才抬头
- 【设计】**弯角的推进独立于状态**。灯带在弯中途必然消失；若丢线就把状态切走、顺带停掉弯角判据，**唯一能终止转向的机制会在最需要它的时候失效**
- 【设计】弯角结束后有**不应期**：刚转完时「灯带横向出画」这个判据仍成立，没有不应期会立刻识别出第二个弯、再转 90°
- 【设计】`FINISH_APPR` 要满足「**全身进入**终点区」：看到黑带后继续前进一段再停。**距离待实测鱼体长度**
- 【设计】硬终止四条全部来自赛题 PDF：脱离 >10s、触壁 3 次、30s 未启动、150s 超时。触壁无传感器信号时用「横向误差持续饱和」推断，**且一次持续饱和只算一次接触**

## 六、时序与算力预算

- 【待验证】控制环频率目标 **≥20 Hz**（欠驱动 + 大滞后）
- 【待验证】灯带提取 ≥30 Hz。标记检测可降频省算力，但**上报延迟会增加**，且受耦合 10 约束
- 【设计】相机采集必须「最新帧覆盖」而非排队，否则延迟随算力抖动累积
- 【待验证】端到端延迟（曝光 → 执行器动作）是全部整定的前提，必须实测

## 七、并发模型（谁在什么时候能写输出）

**这一节防的是一类特定故障：两个各自都「对」的策略同时写同一根摇杆，产生两个都不想要的状态。**

- 【事实】参考项目的输出层 `aim(pwm1, pwm2, pwm3)` 内部是**6 次独立发送**（每通道一条 MAVLink 消息，`move.py:47-54`）。两个执行流各写一部分通道时，这 6 条消息会交错 —— 例如得到「偏航来自转弯策略、前进来自巡线策略」的组合
- 【事实】参考项目本身没有这个问题，因为它只有一个执行流；代价是它把转弯写成了**阻塞主循环 3 秒**的开环动作（[reference-pipeline](reference-pipeline.md) 第 6 节）
- 【推论】所以要并行化的是「感知会阻塞输出」，**不是「轴太多」**

**分工：按「时间尺度 + 会不会阻塞」切，不按轴切。**

| 角色 | 节奏 | 会不会阻塞 | 产出 |
| --- | --- | --- | --- |
| 感知 | 5–15 Hz，抖动大 | **会**（检测推理数百毫秒） | 带时间戳的 `LineObs` / `MarkerCand[]` / `CrossObs`，**不可变** |
| 控制 | **固定 ≥20 Hz**（[第六节](#六时序与算力预算)） | 不会 | 唯一的执行器写点 |
| 日志 / 上报 | 事件驱动 | 不应阻塞控制 | **永不触碰执行器** |

- 【设计】**轴之间经过混控耦合，所以按轴并行等于让两条策略同时写同一根摇杆。**按时间尺度切，才是把「慢且会阻塞」的东西隔离出去
- 【设计】**模式所有权，不是线程优先级。**弯角是 `fsm` 的一个状态、`control` 的一个分支，不是第二个线程；交接点只有一个：`Decision.yaw_override_us`（[第四节](#四数据流)）。**不存在「抢控制权」**——抢意味着结果取决于调度时机，而调度时机不可复现
- 【设计】**共享数据只走「最新覆盖」的队列**（容量 1，满了丢旧帧），不用「共享可变对象 + 锁」。锁只能保证数据不撕裂，保证不了两个策略不打架
- 【设计】**看门狗是必须的，不是可选的。**观测带时间戳，超过阈值未更新就直接回中立/停机。**改成并发之后新增的失败模式是「拿着几秒前的画面自信地开」**——它比参考项目那种「卡死」隐蔽得多，因为程序看起来还在正常工作

**被否掉的方案（记录在案）**

设想：两个线程，一个管全部通道，一个只在转弯时管水平通道，「谁需要谁抢控制权」。否掉的三条理由：

1. **输出会撕裂**：`aim()` 是 6 次发送，交错后能拼出「急转弯 + 全速前进」这种两个策略都不想要、且物理上最容易撞壁的组合
2. **不可复现**：交错与否取决于调度时机，实验室看不出来、比赛现场出；而且出错时没有任何日志能指出是谁发的
3. **它要解决的问题不存在**：真正的痛点是「感知阻塞了输出」，那是时间尺度问题；一个唯一写者 + 独立节拍就解决了，不必引入争用

详细推演见 [logs/2026-10-02-control-concurrency](../logs/2026-10-02-control-concurrency.md)。

## 八、代码组织

### 8.1 算力与部署

- 【事实】赛题 PDF 对运行环境**没有规定**；【推论】但要求「搭载自主控制系统」「检测模块集成于本体」「禁止远程操控」，因此**默认按「全部算力在鱼上」设计**，板外算力只当不可用的优化手段（[operations](operations.md) 的推论）
- 【设计】无论选哪种语言/框架，必须满足三条：
  1. **原始帧可落盘**（排查的唯一证据），且不阻塞控制环
  2. **每个上报决策可回放**：三道闸各自的输入输出都要能打出来
  3. **硬终止独立于状态机**（耦合 9）

### 8.2 包结构：一个扁平包，按层切而不是按人切

- 【事实】当前是一个 **src-layout 的可安装包**：根目录 `pyproject.toml`（2026-10-02 加入）声明 `src/bionic_fish` 为唯一包。`pip install -e .` 之后 `PYTHONPATH=src` 就不再需要，命令行入口是 `python -m bionic_fish`
- 【事实】`src/bionic_fish/` 是**扁平**的：11 个模块、约 4140 行，**没有子包**。每个模块对应第二节分层图里的一层；模块之间的依赖只有「上层拿下层的**数据结构**」，没有「上层调下层的方法」
- 【事实】参考项目的 `packaged_part/` **确实有 4 个业务子包**（`visual` / `move` / `pid_catalog_first` / `camera_gimbal_control`），各自都有 `__init__.py`——所以「参考项目比我们有结构」这句话在**目录层数**上成立
- 【事实】但它的分层依据是**用途/来源**，粘合方式是 `from packaged_part.X.Y import *`：主程序从 5 个子包拉进同一个全局命名空间（`pipe2025_func.py:5-11`）。我们记录的缺陷里，未定义全局 `pwm`、重名的 `PID`、四条 MAVLink 连接，都是这条粘合方式的直接后果（[reference-pipeline](reference-pipeline.md) 6.1 节）
- 【推论】**目录层数不是结构，依赖方向才是。** 判断一层该不该加的判据是「加了它之后，某条边界是不是变成不可能违反」；按作者或按来源分目录做不到这一点，只会让 `import *` 更容易

### 8.3 什么时候才拆子包（拆分触发器）

- 【设计】**现在不拆。** 11 个模块是扁平包的正常规模；子包通常要到二三十个模块才有意义，而且加深度不带来新边界。更直接的理由：**运行顺序只存在于 `runtime.py` 的 `_iterate` 里**（[runtime-flow](runtime-flow.md)），拆更多目录只会让那 43 行更难被找到
- 【设计】**唯一已识别的候选是 `vision.py`**（599 行，含三个互相独立的检测器 + 三个观测结构）。满足任意一条即拆：
  1. `vision.py` 超过约 800 行；
  2. 要加**第四个**检测器；
  3. `MarkerDetector` 需要独立标定（它的 `MarkerParams` 不再与灯带、黑带共用一套）
  拆法：`vision/` 子包 = `observations.py`（三个观测结构）+ `strip.py` + `marker.py` + `crossline.py`，由 `__init__.py` 重新导出，**保持 `from bionic_fish.vision import LineObs` 不变**
- 【设计】**明确不拆 `config.py`**（688 行）。它的体积来自「全部可调参数的唯一住所」这条红线（[不变量 7](invariants.md)）；拆开就等于允许阈值在多处定义，正是那条红线要防的事。**行数不是拆分的理由，边界才是**
- 【设计】当前实现的目录划分与各目录职责见 [`AGENTS.md`](../../AGENTS.md) 的「仓库结构」表（只记目录，不记目录里的文件）

> [!NOTE]
> 当前 `src/` 是**一份参考实现**，用来把上面的约束和踩过的坑固化下来，并让整条链路在没有硬件时也能跑。它**未必适配真机**，后面很可能大改。重写时值得保留的是**模块边界**（第二节）与**耦合约束**（第三节），不是具体代码。
