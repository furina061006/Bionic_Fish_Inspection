# 系统架构：工具链、模块边界与耦合约束

> 入口索引与工作约定在仓库根目录 [`AGENTS.md`](../../AGENTS.md)；本文件是 `.dsh/agents/` 知识库的一部分。
> 场地与规则见 [`competition.md`](competition.md)；硬件输入输出见 [`hardware.md`](hardware.md)；参考项目逆向见 [`reference-pipeline.md`](reference-pipeline.md)。

**本文件状态：混合。**工具链一节是 `【事实】`（用户指定 + 参考项目实证）；模块边界与耦合约束是 `【设计】`，但**其中多数是从实测里逼出来的，不是想出来的**——见 [`logs/`](../logs/)。当前实现（`src/`）是这些约束的**一份参考实现，可能会大改**；改动时应先动本文件，再动代码。

> [!IMPORTANT]
> 本文件记的是**架构**：模块怎么切、为什么这么切、模块之间有哪些必须成立的耦合。代码可以重写，这些约束不能违反——违反任意一条都会产生一整类无法定位的故障。

## 一、工具链（已定）

- 【事实】用户指定：**本项目工具链与 [`reference/pipe_inspector_raspberry-main/`](../../reference/pipe_inspector_raspberry-main/) 一致**。逐项出处见 [reference-pipeline](reference-pipeline.md) 第 1 节
- 【事实】赛题 PDF 对运行环境**没有任何规定**——操作系统、语言、中间件、算力位置全部自由。所以这是**用户的选择**，不是赛题的要求

| 层 | 选择 |
| --- | --- |
| 主控 | 树莓派（Raspberry Pi），Python |
| 相机 | USB 摄像头，OpenCV `VideoCapture` |
| 执行器通信 | **串口直连下位机（默认）**：文本协议，每行一个关节 PWM 微秒值；下位机只做透传（1500µs = 50% 占空比），**不做混控** |
| 控制指令（默认） | 上位机算完再发：`yaw + forward` → `(amplitude, bias)` → 波形线程 → 串口 |
| 飞控通信（备选） | MAVLink over 串口，`pymavlink` |
| 控制指令（备选） | **`RC_CHANNELS_OVERRIDE`**：发的是遥控杆位，飞控负责稳定与定深 |
| 通道布局（备选） | 只有两个轴：`ch_yaw=4` / `ch_forward=5`（照参考平台的 ArduSub 布局猜的，**通道号未确认**；没有深度通道） |
| 检测 | 经典 CV 为主；ONNX Runtime 跑 YOLOv5-Lite 是**保留但未启用**的通路 |
| 外设 | `RPi.GPIO`：声、光 |
| 航向源 | MAVLink `ATTITUDE`。**是否存在未确认**（backlog `#12`） |

**输出节拍是正确性要求，不是性能优化**：

- 【事实】`RC_CHANNELS_OVERRIDE` **会过期**：ArduPilot 官方文档写明「若 MAVLink RC 输入停止，飞控在几秒内回落到常规 RC 输入」，超时由 `RC_OVERRIDE_TIME` 参数配置（[ArduPilot: RC Input](https://ardupilot.org/dev/docs/mavlink-rcinput.html)）
- 【推论】所以「多久发一次指令」与「发什么」同等重要。**一个只在决策变化时才发指令的实现，会在任何超过该超时的停顿里静默失去控制**
- 【待验证】本平台 `RC_OVERRIDE_TIME` 的实际取值（在飞控参数表上读）——它直接决定控制环允许的最大发送间隔
- 参考项目踩到的具体形式见 [reference-pipeline](reference-pipeline.md) 第 6 节；由此推出的并发规则见[第七节](#七并发模型谁在什么时候能写输出)

**车体的轴集合（决定「哪些通道存在」）**：

- 【事实】队内确认（2026-10-02）：**单关节尾鳍** + **一直浮在水面**。所以只有**两个轴**——前进与偏航——**没有深度轴**，也不会有定深环
- 【事实】接口由我们自己设计，没有现成契约；v2 只有 `ch_yaw` / `ch_forward` 两个通道常量（**没有 `ChannelMap` 这个类型**，也没有深度轴）。见 [hardware](hardware.md)
- 【待验证】推进机构自研是否满足原文「基于组委会认证的统一仿生平台改装」的口径——这是**资格问题**，不是技术问题，见 [hardware](hardware.md) 的合规待确认项

**从参考项目继承时要改掉的两条接口习惯**：

1. **只开一条 MAVLink 连接。** 参考项目在 `move.py`、`arm_disarm.arm()`、`disarm()` 里各开一条，三个对象抢同一串口的心跳与消息。**MAVLink 流只有一个读者**——控制输出与遥测必须共用同一条连接。
2. **解锁要校验回执。** 参考项目把 `motors_armed_wait()` 注释掉并**无条件打印 `Armed!`**，解锁失败会静默继续。

## 二、模块边界，以及为什么切在这里

```
     ┌──────────────────────────────────────────────────────────┐
     │  看  vision.py         「这一帧看到了什么」               │
     │    find_white_pipe / find_black_dot / is_tape            │
     └───────────────┬──────────────────────────────────────────┘
                     │  LineObs / Dot 或 None / 黑带有无
     ┌───────────────▼──────────────────────────────────────────┐
     │  主循环  main.py       「一帧里按次序做七件事」            │
     │    ① 四条硬终止 ② 看 ③ 撞壁计数 ④ 上报                    │
     │    ⑤ 判 ⑥ 打舵并发 ⑦ 读下一帧                             │
     └───────────────┬──────────────────────────────────────────┘
                     │  yaw_us / forward_us —— **两个数**
     ┌───────────────▼──────────────────────────────────────────┐
     │  出  link.py           「怎么发出去、怎么对外发信号」      │
     │    MAVLink RC override + 灯 / 蜂鸣 / 播报                 │
     └──────────────────────────────────────────────────────────┘

     进  camera.py（相机帧 + 时间戳）
     参数  params.py（全部可调数字的唯一住所）
     仿真壳（不入包）  sim/ = arena + plant + 假相机 / 假飞控
```

> [!IMPORTANT]
> **v0.1 的五层流水线（感知 / 决策 / 状态 / 控制 / 平台）已经并进 `main.py` 一个循环。**
> 那次分层的收益是每层可单独测试、可并行化；代价是**运行顺序只存在于一处，读任何单个
> 模块都看不出它何时被调用**。审阅者读不懂的正是这一点，所以 2026-10-02 改回线性。
>
> **边界约束本身没有失效**，只是表达方式变了：以前靠"模块之间不互相引用"，现在靠
> "`main.py` 里看得见每一步"。第三节的 12 条耦合一条都没删。
> 演变过程见 [logs/2026-10-02-linear-rewrite](../logs/2026-10-02-linear-rewrite.md)。

**为什么这样切——判据是「排查时分得清哪一层错了」**：

- `perception` 只回答「看到了什么」，**不含任何策略**。它若顺手决定「该不该上报」，那么一次漏报就分不清是**没看见**还是**看见了被否决**——而这正是排查的第一分叉（[troubleshooting](troubleshooting.md)）。
- `reporting` 只做概率判决。它读不到状态机，也不知道车在路线哪一段——这迫使「起终点优先」这类规则必须显式传入上下文，而不是藏在感知里。
- `fsm` 不做像素运算、不做舵量计算，只决定「状态 + 目标速度 + 是否提交转向」。
- `control` 只做「给定目标怎么打舵」，不判断该不该转。
- `platform` 是唯一的硬件出口。**它的存在让整条链路可以在没有硬件的机器上跑完**（回退到记录型实现），这是本仓库现在唯一能验证整链路的原因。

**参考项目恰好把这三件事揉在一起**：一个 `while 1` 循环里同时读队列、跑 PID、判拐角、发 PWM、开线程亮灯抓取，状态用 23 元组在函数间传递。它的 17 条缺陷清单见 [reference-pipeline](reference-pipeline.md) 第 6 节——**清单里超过一半是「边界没切」的直接后果**。

## 三、模块间必须成立的耦合（**最容易漏、漏了最难查**）

这一节是本文最重要的部分。下面每一条都是两个模块之间**必须一起考虑**的关系；任何一条被当成「两个独立模块」处理，都会产生一整类只能靠运气发现的故障。

| # | 耦合 | 后果 / 证据 |
| --- | --- | --- |
| 1 | **转向权限 ∝ 前进速度**（欠驱动尾鳍车没有侧推） | 速度档位 ↔ 弯角 ↔ 丢线恢复三者绑死。弯角把速度降到接近零 → **转不动**，转弯必然超时；丢线恢复不保留前进分量 → **无法回正航向**。实测：弯角速度从中位附近调到 `1525` 后，弯角阶段从 100 帧降到 62 帧 |
| 2 | **「重合」不能用里程判定**（没有里程计） | 上报触发 ↔ 感知：用**固定图像行**判「已到目标下方」，行阈值来自标定。时间更不行——速度一变就错 |
| 3 | **弯角不能靠巡线控制律飞** | `main.py` 的转弯状态 ↔ 航向源 ↔ `drive.py`：管道一离开视野就没有航向参考。必须「**提交一个转向指令 + 用独立判据终止**」。v2 用的是**限时**（参考项目的形状）；按角度终止需要航向源，仍未确认 |
| 4 | **上报的判决阈值由评分决定** | 上报判决 ↔ [`competition.md`](competition.md)：`+5 / −3` ⇒ `p > 3/8` 才值得报；已报满 8 个后上行收益为 0、风险仍为 −3。**v2 目前没有置信度判决**（见 [runtime-flow](runtime-flow.md) 第六节），只保留了「上限 8」这一半 |
| 5 | **起终点黑带与漏油点都是黑的** | `vision.py` ↔ `main.py`：黑带与标记在单帧上不可靠可分，必须**叠加运行上下文**（已经跑够时间才认终点）。这不是纯视觉问题 |
| 6 | **灯带被标记遮挡** | 感知内部：标记就贴在灯带上，会在灯带掩膜上打出一个洞。**被截断的游程其中心会偏向存活的一侧**，直接把中心线拉偏。所以分割的闭运算核必须**大于标记直径**——这是正确性要求，不是平滑 |
| 7 | **像素阈值 ← 标定 ← 相机安装** | `hardware.md` ↔ `vision.py` ↔ `params.py`：相机型号/高度/视场未定，则「3cm 圆对应多少像素」未定，则全部面积/尺寸阈值未定。**代码里不许有未标定的尺寸常数**（[不变量 7](invariants.md)） |
| 8 | **上报与播报必须共用一次触发** | `main.py` ↔ `link.py`：评分把语音单列 10 分（漏播一个 `−2`）。v2 靠「只调一次 `ann.on_report()`」保证 —— **触发点只有一个**，就不会漂移 |
| 9 | **硬终止必须独立于状态判断** | v2 把它们放在**循环体的最前面**（`main.py` 七步的第 1 步），任何状态逻辑都绕不过去。v0.1 只是把 `SafetyMonitor` 与状态转移分开放；放循环头部更强 —— 不是「边界独立」，而是**根本不在同一条控制流里** |
| 10 | **跑太快会来不及看见标记** | 上报 ↔ 速度档位：标记在视野里停留的帧数由**速度 × 帧率 × 视场**决定。v2 的复位判据要求「先看到一个车前的新标记」，所以标记必须有好几帧可见。**速度上限是感知决定的，不只是控制决定的** |
| 11 | **输出只有一个写者，且它的节拍独立于感知** | `drive.py` ↔ `link.py` ↔ `vision.py`：RC override 会超时（第一节），所以「发指令」必须有自己的时钟；而若两个策略各写一部分通道，`aim()` 内部那 6 次独立发送会交错出「一边急转、一边全速」这种两个策略都不想要的状态。**控制权是显式的模式所有权，不是线程优先级** → [第七节](#七并发模型谁在什么时候能写输出) |
| 12 | **单关节尾鳍：推力与转向出自同一个执行器** | `drive.py` ↔ `hardware.md` ↔ `sim/plant.py`：尾摆**振幅**给推力、**偏置**给转向，所以**大舵量直接吃掉推力**。注意这与耦合 1 不是一回事——耦合 1 是「权限随速度变化」（两个独立轴），这里是**同一个量被两个用途争**。因此转向需求与推进需求必须**一起**决策（预算分配），不能各算各的再加起来。**实现状态（2026-10-13）**：机制在 `drive.synthesize_tail_fin()` 里（两套量纲分别归一化 + `|偏置|·w + |振幅| <= tail_fin_budget`），但**默认 `tail_fin_budget = None`（关闭）** —— 打开后合成场地过不了弯角，而占位动力学已知是错的、不能拿它整定。`sim/plant.py` 现把两者当独立轴，**在这个意义上已知是错的**，换真机前必须重建模 → [hardware](hardware.md) |

## 四、数据流

```
相机帧
  ↓ perception：灯带分割 → 逐行游程 → 鲁棒直线拟合
  │    LineObs { valid, e_y_px, e_theta_rad, curvature, width_px,
  │               confidence, lookahead_px, fit }
  ↓ perception：黑帽 → 连通域 → 形状/面积门控 + 与中心线的横向门控
  │    Dot { u, v, diameter_px, val }
  ↓ perception：灰度暗带 + 行跨度 + 必须横跨灯带 + 必须在画面内部 + 必须灯带可见
  │    bool（是不是起终点黑带）
  ↓ main：黑点越过 report_row 且不在「已报」状态 → 亮灯 + 播报（**同一次调用**）
  ↓ main：四条硬终止 → 巡线 / 转弯 / 找线 / 终点
  ↓ drive：外环 atan2(e_y, L) → 内环 (e_theta + 修正量) → 舵量
  │    yaw_us / forward_us —— **两个数，不是对象**
  ↓ main：`link` 有没有 `send_tail_fin` —— **出口唯一的分叉点**
  ├─ 有（`TailFinLink`，默认）：合成 + 波形
  │    drive.synthesize_tail_fin(yaw, forward) → (amplitude, bias)
  │    fin.TailFinWaveform（线程 100 Hz）→ 串口每行一个 µs 值 → 下位机 → 舵机 PWM
  └─ 没有（`MavlinkLink` / `SimLink`）：link.send(yaw, forward)
       link：RC_CHANNELS_OVERRIDE（未用通道填 65535 = 不覆盖）
```

**几处刻意的不对称，都是踩过坑才有的**：

- `e_theta` 是**灯带方向 − 车体航向**（灯带相对车体），所以内环误差是 **`e_theta + e_theta_d`**，不是看起来更自然的差。写成差会让航向环变成**正反馈**——而「直道 + 横向偏置」的测试**看不出来**（那里 `e_theta ≡ 0`）。
- `valid=false` 与「偏差 = 0」是两件事。**严禁用 0 冒充「没看到」**（[不变量 3](invariants.md)）。
- v0.1 的 `lateral_reliable` 字段没有了：横向门控移进 `find_black_dot` 内部。**代价是「被横向门控拒掉」与「根本没看见」在观测里长得一样** —— 这是 v2 丢掉的一处可诊断性。
- `is_tape` 只在**管道可见**时才可能为真 —— 「横穿管道」这个事件没有管道就没有定义。
- 没有 `ReportEvent` 对象了：灯、蜂鸣、播报由 `main.py` 里**同一次 `on_report()` 调用**驱动，序号就是 `reports` 计数器。**触发点只有一个**，所以不会「报了不播」。

## 五、状态与硬终止

v0.1 是一个 8 状态机（`IDLE / ALIGN / FOLLOW / CORNER / LINE_LOST / FINISH_APPR / DONE / ABORT`）。
v2 把它压成**循环里的一个字符串加四个 `if`**，行为一条没少：

```
每帧开头（绕不过去）：
    超 150s → 结束      撞壁满 3 次 → 结束
    30s 未启动 → 结束    （鱼动过之后才算）脱离路线 >10s → 结束
然后：
    看到终点黑带且跑够时间 ──▶ 终点（继续蠕行，整条鱼压过黑带，然后结束）
    正在转弯 ── 转过最短时间后重新看见管道 ──▶ 巡线
             └─ 超过转弯时限 ─────────────▶ 找线
    看不见管道 ─────────────────────────▶ 找线
    管道曲率大 / 可用行占比低 ──────────▶ 转弯
    都不是 ────────────────────────────▶ 巡线
```

- 【设计】**起点区不单独成状态了**：v0.1 有一个 `ALIGN` 段专门把航向对齐管道，理由是起点区
  只有约 500mm、初始航向误差大会压到分界线。v2 直接从巡线开始 —— 简单一档，代价是起点
  偏得厉害时会先晃一下。**这一条是先跟参考项目（它也没有 ALIGN）**，现场看效果再决定要不要补
- 【设计】弯角判据是 **`confidence` 下降为主、`curvature` 突增为确认**。实测：逼近直角时
  `confidence` 单调 0.93→0.49，而 `curvature` 只在最后 50mm 才抬头。两者任一触发即进转弯
- 【设计】**转弯的推进不依赖管道可见**。管道在弯中途必然消失；若丢线就把状态切走、顺带停掉
  转弯判据，**唯一能终止转向的机制会在最需要它的时候失效**。所以转弯分支排在丢线分支之前
- 【设计】转弯结束有**不应期**：刚转完时「管道横向出画」这个判据仍成立，没有不应期会立刻
  识别出第二个弯、再转 90°
- 【设计】终点要满足「**全身进入**终点区」：看到黑带后继续前进 `finish_creep_s` 再停。
  **这个时长待实测鱼体长度**
- 【设计】硬终止四条全部来自赛题 PDF：脱离 >10s、触壁 3 次、30s 未启动、150s 超时。触壁无
  传感器信号时用「横向误差持续饱和」推断，**且一次持续饱和只算一次接触**
- 【事实】**次序有语义**：「未启动」排在「脱离路线」之前，而且脱线**只在鱼动过之后才算**。
  否则一条从没启动的鱼会被记成「跑丢了」，**日志会把排查引向错误的方向**

## 六、时序与算力预算

- 【待验证】控制环频率目标 **≥20 Hz**（欠驱动 + 大滞后）
- 【待验证】灯带提取 ≥30 Hz。标记检测可降频省算力，但**上报延迟会增加**，且受耦合 10 约束
- 【设计】相机采集必须「最新帧覆盖」而非排队，否则延迟随算力抖动累积
- 【待验证】端到端延迟（曝光 → 执行器动作）是全部整定的前提，必须实测

## 七、并发模型（谁在什么时候能写输出）

**这一节防的是一类特定故障：两个各自都「对」的策略同时写同一根摇杆，产生两个都不想要的状态。**

- 【事实】参考项目的输出层 `aim(pwm1, pwm2, pwm3)` 内部是**6 次独立发送**（每通道一条 MAVLink 消息，`move.py:47-54`）。两个执行流各写一部分通道时，这 6 条消息会交错 —— 例如得到「偏航来自转弯策略、前进来自巡线策略」的组合
- 【事实】参考项目本身没有这个问题，因为它只有一个执行流；代价是它把转弯写成了**阻塞主循环 3 秒**的开环动作（[reference-pipeline](reference-pipeline.md) 第 6 节）
- 【推论】所以要并行化的是「感知会阻塞输出」，**不是「轴太多」**

**分工：按「时间尺度 + 会不会阻塞」切，不按轴切。**

| 角色 | 节奏 | 会不会阻塞 | 产出 |
| --- | --- | --- | --- |
| 感知 | 5–15 Hz，抖动大 | **会**（检测推理数百毫秒） | 带时间戳的 `LineObs` / `Dot`，**不可变** |
| 控制 | **固定 ≥20 Hz**（[第六节](#六时序与算力预算)） | 不会 | 唯一的执行器写点 |
| 日志 / 上报 | 事件驱动 | 不应阻塞控制 | **永不触碰执行器** |

- 【设计】**轴之间经过混控耦合，所以按轴并行等于让两条策略同时写同一根摇杆。**按时间尺度切，才是把「慢且会阻塞」的东西隔离出去
- 【设计】**模式所有权，不是线程优先级。**弯角是 `fsm` 的一个状态、`control` 的一个分支，不是第二个线程；交接点只有一个：`main.py` 里的 `yaw` 变量（转弯时它取固定值，见 [第四节](#四数据流)）。**不存在「抢控制权」**——抢意味着结果取决于调度时机，而调度时机不可复现
- 【设计】**共享数据只走「最新覆盖」的队列**（容量 1，满了丢旧帧），不用「共享可变对象 + 锁」。锁只能保证数据不撕裂，保证不了两个策略不打架
- 【设计】**看门狗是必须的，不是可选的。**观测带时间戳，超过阈值未更新就直接回中立/停机。**改成并发之后新增的失败模式是「拿着几秒前的画面自信地开」**——它比参考项目那种「卡死」隐蔽得多，因为程序看起来还在正常工作

**被否掉的方案（记录在案）**

设想：两个线程，一个管全部通道，一个只在转弯时管水平通道，「谁需要谁抢控制权」。否掉的三条理由：

1. **输出会撕裂**：`aim()` 是 6 次发送，交错后能拼出「急转弯 + 全速前进」这种两个策略都不想要、且物理上最容易撞壁的组合
2. **不可复现**：交错与否取决于调度时机，实验室看不出来、比赛现场出；而且出错时没有任何日志能指出是谁发的
3. **它要解决的问题不存在**：真正的痛点是「感知阻塞了输出」，那是时间尺度问题；一个唯一写者 + 独立节拍就解决了，不必引入争用

详细推演见 [logs/2026-10-02-control-concurrency](../logs/2026-10-02-control-concurrency.md)。

## 八、代码组织

### 8.1 算力与部署

- 【事实】赛题 PDF 对运行环境**没有规定**；【推论】但要求「搭载自主控制系统」「检测模块集成于本体」「禁止远程操控」，因此**默认按「全部算力在鱼上」设计**，板外算力只当不可用的优化手段（[operations](operations.md) 的推论）
- 【设计】无论选哪种语言/框架，必须满足三条：
  1. **原始帧可落盘**（排查的唯一证据），且不阻塞控制环
  2. **每个上报决策可回放**：候选的 `Dot.val` 与判定条件（`report_row` / `reports < max_reports` / `in_dot`）都要能打出来。**v2 尚未实现落盘与可视化**，这一条现在不成立
  3. **硬终止独立于状态机**（耦合 9）

### 8.2 包结构：一个扁平包，按层切而不是按人切

- 【事实】当前是一个 **src-layout 的可安装包**：根目录 `pyproject.toml`（2026-10-02 加入）声明 `src/bionic_fish` 为唯一包。`pip install -e .` 之后 `PYTHONPATH=src` 就不再需要，命令行入口是 `python -m bionic_fish`（**注意 `bionic-fish` 这个脚本现在是指向不存在的函数，见 [backlog](../../backlog.md)）
- 【事实】`src/bionic_fish/` 是**扁平**的：7 个文件、约 1330 行，**没有子包**。每个模块对应第二节分层图里的一层；模块之间的依赖只有「上层拿下层的**数据结构**」，没有「上层调下层的方法」
- 【事实】参考项目的 `packaged_part/` **确实有 4 个业务子包**（`visual` / `move` / `pid_catalog_first` / `camera_gimbal_control`），各自都有 `__init__.py`——所以「参考项目比我们有结构」这句话在**目录层数**上成立
- 【事实】但它的分层依据是**用途/来源**，粘合方式是 `from packaged_part.X.Y import *`：主程序从 5 个子包拉进同一个全局命名空间（`pipe2025_func.py:5-11`）。我们记录的缺陷里，未定义全局 `pwm`、重名的 `PID`、四条 MAVLink 连接，都是这条粘合方式的直接后果（[reference-pipeline](reference-pipeline.md) 6.1 节）
- 【推论】**目录层数不是结构，依赖方向才是。** 判断一层该不该加的判据是「加了它之后，某条边界是不是变成不可能违反」；按作者或按来源分目录做不到这一点，只会让 `import *` 更容易

### 8.3 什么时候才拆子包（拆分触发器）

- 【设计】**现在不拆。** 7 个文件是扁平包的正常规模；子包通常要到二三十个模块才有意义，而且加深度不带来新边界。更直接的理由：**运行顺序就是 `main.py` 一个循环**（[runtime-flow](runtime-flow.md)），拆更多目录只会让那 257 行更难被找到
- 【设计】**唯一已识别的候选是 `vision.py`**（343 行，三个纯函数 `find_white_pipe` / `find_black_dot` / `is_tape` + 两个观测结构 `LineObs` / `Dot`）。满足任意一条即拆：
  1. `vision.py` 超过约 800 行；
  2. 要加**第四个**检测器；
  3. `find_black_dot` 需要独立标定（它的参数不再与管道、黑带共用一套）
  拆法：`vision/` 子包 = `observations.py`（`LineObs` / `Dot`）+ `pipe.py` + `dot.py` + `tape.py`，由 `__init__.py` 重新导出，**保持 `from bionic_fish.vision import LineObs` 不变**
- 【设计】**明确不拆 `params.py`**（约 290 行）。它的体积来自「全部可调参数的唯一住所」这条红线（[不变量 7](invariants.md)）；拆开就等于允许阈值在多处定义，正是那条红线要防的事。**行数不是拆分的理由，边界才是**
- 【设计】当前实现的目录划分与各目录职责见 [`AGENTS.md`](../../AGENTS.md) 的「仓库结构」表（只记目录，不记目录里的文件）

> [!NOTE]
> 当前 `src/` 是**一份参考实现**，用来把上面的约束和踩过的坑固化下来，并让整条链路在没有硬件时也能跑。它**未必适配真机**，后面很可能大改。重写时值得保留的是**模块边界**（第二节）与**耦合约束**（第三节），不是具体代码。
