# 文档写法（标记约定、Markdown 技巧、仓库文案）

> 入口索引与工作约定在仓库根目录 [`AGENTS.md`](../../AGENTS.md)；本文件是 `.dsh/agents/` 知识库的一部分。

**这里放「怎么写」**：所有仓库内 Markdown 的格式技巧与文案约定。**这类细节不要在 `AGENTS.md` 里展开**——它在每轮上下文里，只放索引 + 红线 + 路由表。以后遇到新的写法坑，加到这里，别加回索引。

## 状态标记：`【事实】` / `【设计】` / `【待验证】`

本仓库的文档里同时装着「赛题规定的」「我们打算做的」和「还没验过的假设」，光读文字分不出区别。因此约定三类标记，**每条实质性陈述都要能归入其中一类**：

> [!NOTE]
> 这一节最初写于 2026-09-25，当时的说法是「当前几乎没有可执行代码」——**那句话现在不成立了**（`src/` 已有约 4100 行）。但标记约定的理由与代码量无关：它区分的是**依据的强度**，而不是「有没有代码」。`src/` 里同样有大量 `UNVERIFIED` 的常量需要同样的纪律。

| 标记 | 含义 | 依据来源 | 可否写进代码常量 |
| --- | --- | --- | --- |
| `【事实】` | 赛题文件 / 官方规则 / **实测结果** | 必须能指到出处（原文页码、实测记录） | 可以 |
| `【设计】` | 本队已决定的技术方案 | 团队决定；改动需要沟通 | 可以（但改方案要同步改文档） |
| `【待验证】` | 假设、推算、未确认的接口 | 无 | **不可以** |
| `【推导】` | 由 `【事实】` 数字算出的结论 | 算式要写出来 | 可以（属于结论） |
| `【推算】` | 由物理 / 几何量级估算出的结论（`【推导】` 的估算变体） | 假设与公式要写出来 | 可以，但假设必须显式写出 |
| `【推论】` | 由已有结论逻辑推出的结论（`【推导】` 的逻辑变体） | 前提要写出来 | 可以 |

三个派生标记（`【推导】` / `【推算】` / `【推论】`）的区别只是**依据类型**：数字算式 / 物理量级估算 / 逻辑推理。不要为了统一而混用，因为读者据此判断结论的适用范围——估算可以宽松，算式必须精确。

配套规则：

- **依据来源的合法性**：`【事实】` 只能来自 (a) `docs/` 里的赛题 PDF、(b) 组委会 / 平台方的官方材料、(c) 本项目自己做出的实测。**其它项目不是来源**——队内招新题、往届作品、邻近比赛、开源工程、开发机上装了哪些库，这些只能用来**产生待验证的假设**，必须标 `【待验证】`，并且要写清「需向组委会确认」。
- **`【待验证】` 被证实或证伪后，必须回到对应文档把标记改成 `【事实】` 或删掉，并写清依据。** 一个永远不摘的 `【待验证】` 会让整个知识库失去可信度
- 推算类的 `【推算】` 要写出假设与算式（例如相机视场表要给出 `W ≈ 2·h·tan(HFOV/2)`），否则读者无法判断结论的适用范围
- 两份文档不要复制同一份事实性表格：`【事实】` 类数字只写在 [`competition.md`](competition.md)，其它文档引用它（[不变量 9](invariants.md)）
- **唯一的例外是 `AGENTS.md` 的红线**：红线必须在「不翻开任何文档」的前提下就能执行，所以允许在红线行内直接写出阈值，但同一行必须给出所属文档的链接
- 允许存在**派生视图**（例如 `hardware.md` 的约束表、`strategy.md` 的速度换算表），条件是：表前明确写出「这是 X 的派生视图」并链接到唯一权威。判定标准是——**权威改了，派生视图跟着改是对的；派生视图自己改了而权威没动，就是错**

## 加粗不要写成 `**「x」**`

`**` 紧贴前面的文字、右边紧跟 `「`（标点）时，按 CommonMark 的 flanking 规则**开不了强调**，预览里会原样显示 `**`：

| 写法 | 结果 |
| --- | --- |
| `点一下**「重新加载」**` | ❌ 显示字面 `**`（前面 `下` 是文字、右边 `「` 是标点，开标记只满足 right-flanking） |
| `点一下「**重新加载**」` | ✅ 加粗 |
| `**「重新加载」**` 出现在行首或空格 / 标点之后 | ✅ 能加粗，但为统一仍建议写成上一种 |

**规则**：加粗范围正好是引号里的文字就用 `「**x**」`；整句加粗就用 `**整句**`。**不要把 `**` 夹在文字与 `「` 之间。**

**自查**：没有测试守着这类问题。可疑点是 `**「` 前面紧贴文字、或 `」**` 后面紧跟文字；准确判定要按 flanking 规则配对 `**`（列表项 / 表格行 / 标题各自成块，行内代码按「文字」占位）。

## 日志是存档，不改写正文

`.dsh/logs/` 下的日期日志是**当时的过程快照**。发现旧日志写错了、过时了，**不要改它的正文**——在当天的日志或新日志里说明即可。

结论变化的分工：

- **现行事实与设计** → `.dsh/agents/`（改完把标记一起更新）
- **过程与根因**（为什么这么定、试过哪些死路） → `.dsh/logs/`
- **知识库自身的变更** → 各文档末尾的「变更记录」表

## 链接必须可达

- 所有跨文件链接用**相对路径**，从当前文件出发计算（例如 `.dsh/agents/vision.md` 指向 `../../AGENTS.md`）
- 指向章节时带上锚点，锚点按标题文字（中文标题的锚点就是标题本身去掉标点）
- **改文件名 / 搬目录时，要在同一次改动里修完所有入站链接**；`.dsh/agents/` 里的文档被 `AGENTS.md` 的路由表引用，漏改就会出现死链
- 文档里引用的图片放在 `docs/images/`，用相对路径引用
- **改完文档必须跑链接校验**：`python3 .dsh/tools/check-links.py .`。它会把 fenced code block 里的示例剔掉，再逐个解析相对链接与标题锚点；锚点按 GitHub 规则生成（只保留字母 / 数字 / 组合标记与 `-` `_`，其余标点与符号全部丢弃），所以中文标题里的全角括号不会进锚点
- 文件名含 `(` `)` 等 Markdown 链接保留字符时，链接目标要**百分号转义**（`(` → `%28`、`)` → `%29`），否则链接会被括号提前截断。本仓库的赛题 PDF 就是这种情况

## 代码注释：不写导航块

2026-10-02 的线性重写**删掉了**每个模块 docstring 末尾的中文「在链路里的位置」块。

为什么要删：那些块是为了补一个洞 —— v0.1 的「每帧转一圈」让顺序**只存在于一个地方**，
任何单个模块里都看不见。加块是对症下药，但**药下错了地方**：真正的问题是结构，不是注释。
结构改线性之后，`main.py` 从上往下读就是顺序，块就没有存在理由了。

由此定下的写法：

- **注释解释「为什么」，不解释「在哪里被调用」**。调用位置由结构本身表达
- 容易踩错的地方必须留注释，尤其是**踩过坑才认识到的**（例如 `drive.py` 的
  `heading_error` 为什么是加不是减）—— 这类注释是资产，不是噪音
- 代码细节与 docstring 用英文，与代码一致；**跨模块的设计理由写进 `.dsh/agents/`**，
  不要在代码里写第二份

### 长函数用分节，不要用抽函数

`main.py` 的循环有 109 行代码，偏长。试过的办法是**分节**而不是抽函数：

```
        # ==================================================================
        # 4. 上报
        # ==================================================================
        # 一次「看见 → 经过」算一个点……（说明集中写在这里）
        # 不能写成「黑点离开画面」：……（踩过的坑也写在这里）
        if dot is None:
            ...
```

四条约定：

1. **节标记统一成 `# ===== N. 名称 =====`**，缩进与该节的代码一致 —— 这样编辑器折叠是干净的
2. **一节的说明集中写在节标题下面**，不要散在代码行之间。行内只留 1~4 行的就近说明
3. 模块 docstring 里放一份「折叠后应该看到的样子」，对着它确认折叠有没有生效
4. **抽函数的判断标准是「有没有私有状态」，不是行数**：有私有状态的机制（计数器、去重器）
   可以搬走；纯粹的决策**不要搬** —— 搬走之后读代码的人必须跳过去才能理解顺序，
   而顺序往往正是那段逻辑的全部价值

【推论】分节和抽函数**都不减少总阅读量**。区别是分节把长度换给**可折叠性**，而折叠是编辑器
免费给的 —— 所以同样要达到「看起来短」，分节比抽函数划算。代价是**源文件变长**（说明不再
复用行内空间），这是明知的交易。详见 [logs/2026-10-02-doc-alignment-and-sectioning](../logs/2026-10-02-doc-alignment-and-sectioning.md)

## 其它既有约定

- **行内代码**（反引号）用于路径、键名、命令、字段名、状态名：`.dsh/agents/`、`LineObs`、`e_y`、`steer`、`LineObs.valid`、`p > 3/8`
- **数字要带单位与来源**：`260 ± 20 mm`【事实】、`0.375`【推导】。裸数字不许出现
- **表格优先于长段落**：本仓库大量内容是「条件 → 动作」「现象 → 原因」的映射，表格比段落更快被检索
- **每份 `.dsh/agents/` 文档开头有三件事**：指回 `AGENTS.md` 的引用块、本文件状态说明、以及「相关文档」的链接。新文档照抄这个开头
